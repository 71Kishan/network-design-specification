# Requirements-to-Design Traceability

This document connects the project's observed requirements to the analysis evidence and proposed design responses.

| Requirement area | Evidence recorded in project | Design response |
|---|---|---|
| Network / Internet capacity | 50 Mbps symmetrical service; user reports and traffic analysis identified delays during higher activity and large cloud transfers | Evaluate higher-speed business connectivity, including the documented 500/500 Mbps and 940/940 Mbps options |
| Workstation performance | Slow login/readiness behavior and limited RAM were documented on the existing endpoint fleet | Replace the documented Dell Inspiron 5000 fleet with proposed business-class notebooks |
| Server-room environment | Existing rack was identified as insufficient in size/cooling | Provide a larger 42U rack with active cooling |
| Wireless performance | Wi-Fi mapping assessed signal strength, connectivity, speed, and user observations | Improve wireless/network capacity as part of the broader connectivity upgrade |
| Workplace ergonomics | Existing desks had limited height/adjustment capability | Introduce adjustable sit/stand desks |

## Traceability logic

The project followed a simple design chain:

**Observed condition → requirement → analysis → proposed response → implementation plan**

This traceability is important because the project was a proposed design exercise rather than a production deployment. The repository does not present the proposed responses as validated post-implementation results.

## Evidence boundaries

The source material supports the existence of the requirements-gathering, analysis, design, and planning activities. It does not provide post-deployment measurements proving that the proposed changes improved performance, because the student team did not perform the production deployment.
